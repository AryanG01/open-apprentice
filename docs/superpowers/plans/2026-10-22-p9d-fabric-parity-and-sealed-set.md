# Plan 9D: Fabric campaign contract, cross-backend parity, and the private sealed set

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The same learned banner→story layout (one rule, no per-backend rule) runs through the same reference procedure on real Fabric as on Konva, and every development fixture/outcome passes the independent verifier against its gold on both; then a private sealed set (owner-authored banners + gold, never committed) can be evaluated on both backends to support, or refute, a generalization claim.

**Architecture:** The Fabric dispatcher gains the campaign node types as genuine Fabric objects: artboards and the CTA as `fabric.Group` with a fixed layout, text as `fabric.Textbox`, images as `fabric.FabricImage`, the CTA plate as `fabric.Rect` with `rx/ry`. Fabric's own coordinate semantics are kept (children of a group are positioned relative to the group's centre); `nativeState` reports raw Fabric attributes plus a `frame` tag, and the independent verifier composes positions itself. The badge lane's flat-rect behaviour and its private drift are untouched. Parity is measured, not assumed: one table, both backends, every fixture/outcome. The sealed set is tooling plus an owner authoring step; nothing about its contents is generated by the agent.

**Tech Stack:** Fabric 6.9.1 in the locked page, Konva unchanged, Python 3.12, existing campaign/evaluation packages, `oa` CLI (typer).

**Spec:** `docs/superpowers/specs/2026-10-22-promo-story-card-design.md` (§2 goal 6, §7.8 private sealed set, §7.9 held-out axis, §8, §9 steps 9-10).

**Plan 4 of 4.**

## Global Constraints

- All 9A-9C constraints hold. In particular: one learned rule for both backends; the reference procedure is the same JSON-AST program; origins `search|model|reference|builtin`.
- The Fabric badge lane must not change: flat rect scenes, its tool behaviour, its private `move_origin: center` drift, and `services/engine/test/fabric.test.js` stay green. Campaign node types are additive.
- The verifier composes geometry itself from raw native attributes; the engine never converts Fabric coordinates for it.
- The sealed set lives only under `benchmarks/final/campaign/` (git-ignored). Only its sha256 manifest is committed. Agent-visible packages never read it (import-linter + path rule). Banners and gold in it are authored by the owner, not generated by the agent.
- No parity or generalization claim in docs or UI until the corresponding table is produced by a real run; a blocked or failing row is reported as such.

## Review Focus

1. A Fabric `Textbox` silently widens itself to fit a long word (`dynamicMinWidth`), which hides `word_too_wide`; the Fabric `observe_fit` and the verifier must still report it.
2. Fabric reports image size as natural size × scale: the gold comparison and every size check must use effective size, not raw width.
3. A group child's position in Fabric is relative to the group's centre; a verifier that reads it as top-left passes the wrong layout. Pinned by a Fabric scene whose correct reading and naive reading differ.
4. The Fabric badge flow (flat rects, drift, repair) behaves exactly as before.
5. A sealed set with a missing gold, a duplicated fixture id, or a hash that no longer matches the committed manifest is refused before any run.

Each is pinned by a test in the owning task.

- Layout of `benchmarks/final/campaign/`: `banners/<id>.json` (fixture format, 9A) and `gold/<id>.<outcome>.json` (gold format, 9A), authored by the owner in an editor or by hand.
- `validate_set(root: Path) -> list[str]` — problems: missing gold for a banner's expected outcome, duplicate ids, ids colliding with public fixtures, non-Liberation fonts, unknown assets (Review Focus 5).

- `run_sealed(root, manifest, engine_url, token) -> dict` — refuses if any hash differs from the committed manifest; learns from the public teaching pair only; runs every banner on both backends (answering questions with the gold's outcome, recorded as such); verifies against the sealed gold; writes `results/campaign_sealed/<date>/report.md` (git-ignored) and prints the summary.
- `campaign_sealed_howto.md`: how the owner authors banners and gold (format, roles, the frozen limits, what makes a banner "held out"), how to seal, and the rule that the set is frozen once sealed.
